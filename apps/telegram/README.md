# tg — the Telegram client

The reference app, and the reason the SDK exists. Currently a **mock chat**: the UI is
real and runs on the E72, the protocol is not written yet.

## Two crates, on purpose

```
apps/telegram/          tg          rlib,      host-testable, no runtime items
apps/telegram/device/   tg-device   staticlib, the three entry points the shim calls
```

`tg` is a plain rlib with no `#[global_allocator]` and no `#[panic_handler]`, which is
what lets `cargo test` run the chat logic on the host. Every decision the app makes —
what a row looks like, where a bubble breaks, what a key does — lives here and is tested
without a phone.

`tg-device` carries the runtime items and does nothing else: it translates `ShimEvent`
into `KeyEvent`, wraps the shim's framebuffer in a `Canvas`, calls `handle_key` and
`draw`, and presents. Anything in it that looks like a policy decision is in the wrong
crate.

`tg-device` is **not** a member of the root workspace, and cannot be: a crate that
defines `#[panic_handler]` fails to build for the host, because cargo links the test
harness against `std`, which already defines it. It is its own workspace root with its
own `target/`, and only ever builds for ARM.

## Modules

| | |
|---|---|
| `model` | `Chat`, `Message`, `Delivery`, and `Store::mock()` |
| `chats` | The conversation list |
| `conv` | The transcript: bubble layout, grouping by sender, per-message gap |
| `lib` | `App` — the screen enum and the key routing between them |

## Building and running

```
cargo test -p tg                       # the chat logic, on the host
cargo run  -p preview                  # renders every screen to preview-out/*.png
tools/symbuild apps/telegram           # → apps/telegram/build/telegram.sis
```

`app.conf` holds the whole manifest. `UID3` there becomes three things that must agree —
the E32 header's UID3, the UID3 in `data/telegram_reg.rss`, and `KUidShimApp` in the shim
via `-DSHIM_APP_UID3` — and `symbuild` wires all three from that one value. Getting them
out of step produces the least debuggable failure this platform has: AppArc finds a
registration for a UID no installed binary claims, so the icon appears and tapping it does
nothing at all, with no error and no log.

The icon is generated by `data/mkicon.py` and not committed. A checked-in `.bmp` is a
binary nobody can review; the generator is the source.

## What is real and what is not

Real, and confirmed on the device: the chat list, scrolling and selection, opening a
conversation, the transcript with bubble grouping, typing into the composer, the softkey
bar, going back.

Not written: MTProto. What that needs, measured rather than estimated:

- **Crypto.** The public SDK gives SHA-1 and MD5 only. Open C's OpenSSL 0.9.8a — *if the
  handset has it*, which `examples/libprobe` exists to answer — adds AES, RSA,
  `BN_mod_exp` and `RAND_bytes`, but not SHA-256, which MTProto 2.0 uses everywhere. So
  SHA-256 gets written in Rust regardless.
- **TCP.** Eight shim functions, none written. `RSocket` as a `CActive` plus IAP
  selection. This is the item with real platform risk.
- **Storage.** Done — see [`symbian::fs`](../../crates/symbian).
- **TL serialization.** `api.tl` has 2449 declarations; a working client needs ~100–150 of
  them, which wants a generator rather than hand-writing, because a silent constructor
  mismatch is unrecoverable to debug on a phone.
- **`api_id`/`api_hash`** from my.telegram.org. The only item that cannot be worked
  around.

The order that keeps the risk last: storage (done) → crypto → TCP.
